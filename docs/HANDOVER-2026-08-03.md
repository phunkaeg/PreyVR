## What this lane was asked to do

Take H-001 — "does the shipping renderer expose or retain a stereo/multi-view rendering path?" —
while Codex worked OpenXR. H-001 was chosen because it was the largest unanswered architectural
question and had no file overlap with the OpenXR lane.

## Headline result: H-001 is closed, fully negative

**There is no retained stereo path and no multi-view render structure. The per-eye route must be
mod-owned.** This is now a decided question rather than an assumption, and it was settled before
anyone built on the cheaper hypothetical.

Two independent methods agree.

**Stereo half.** `Stereo` occurs exactly 7 times in the whole 48 MB image and `stereo` 3 times, and
every occurrence is accounted for: two orphaned Flow Graph node names, a volumetric-cloud cvar, a
Scaleform cvar, two help strings, and two audio channel configurations. Zero matches for `r_Ster`,
`StereoMode`, `Oculus`, `OpenVR`, `OSVR`, `SteamVR`, `HmdDevice`, `IHmd`, `LeftEye`, `RightEye`.

The clincher: the surviving `Stereo:StereoParameters` flownode's ports are `CurrentEyeDistance`,
`CurrentScreenDistance`, `CurrentHUDDistance`. In stock CryEngine those write `r_StereoEyeDist`,
`r_StereoScreenDist`, `r_StereoHudScreenDist` — **none of which exist here**. The registration
survived; its cvar targets were stripped.

**Multi-view half.** A live read-only ReGenny probe found the real per-frame view block and ran an
orthonormal-camera census: **exactly one camera per frame slot**, in both stationary and moving
states.

The decisive discriminator was the player standing still. The two frame slots were **byte-identical,
separation `0.00000`**. A left/right eye pair must differ by a constant lateral IPD offset at all
times, including at rest. Identical slots cannot be eyes — they are MT/RT frame double-buffers.

Captures: [`../captures/traces/2026-08-01-prey-stereo-path-recon.md`](../captures/traces/2026-08-01-prey-stereo-path-recon.md)
and [`../captures/traces/2026-08-01-prey-multiview-probe.md`](../captures/traces/2026-08-01-prey-multiview-probe.md).

### R-026 is the most useful thing found

Renderer `+0x4A08`, stride `0x328`, two slots indexed by `+0x499C`. Within a slot:

| Offset | Field |
| --- | --- |
| `+0x240` | `Matrix33` rotation, verified orthonormal, row 1 is up (CryEngine forward=Y/up=Z) |
| `+0x264` | camera world position (copy at `+0x230`) |
| `+0x270` | frustum left, right, bottom, top — **four independent values** |
| `+0x280` | near `0.1` / far `8000.0` |
| `+0x040` | aspect |

Proven live: position moved `0.67244` units over 100 frames while walking, with head bob visible in
Z. Never written to.

Why it matters: OpenXR requires asymmetric per-eye projection where `L != -R`. Because this block
already stores each frustum edge separately, asymmetric frusta are directly representable without
restructuring the camera. The project now has **two** candidate pose-injection points — this and the
R-009 `ArkPlayerCamera::UpdateView` callback — and which is authoritative is unresolved.

## Traps found the hard way

**F-002 — ReGenny `+N` is a delta, not an absolute offset.** In this build `+N` places a field N
bytes after the *previous field's end*, contrary to ReGenny's own documentation. The pre-existing
`PreyRendererGraphics` had been silently wrong since it was written: `swapchain` resolved to
`+0xAE90`, `swapchain_mirror` to `+0x36C58`. An overlay read returned
`(-1635.07, -7952.76, 6753.18)` where the truth was `(783.58, 1573.48, 17.10)`.

It survived because every prior finding came from x64dbg, Cheat Engine, or direct address
arithmetic — nobody had ever read a value *through* an overlay. All three structs are rewritten with
correct deltas and a warning header, verified **21 of 21 fields against direct arithmetic**. No
existing finding was affected. Rule: never trust an overlay value until it is diffed against a
direct read at the same absolute address.

**Ghidra analysis discarded two annotations.** The full auto-analysis pass wiped the
`BeginRendererScene` and `EndRendererScene` renames and plate comments while all 24 `Ark*`
annotations survived. Both are restored with full evidence comments and the program is saved.
Re-verify after any future analysis pass.

**Mid-analysis readings are worthless.** I sampled the database while the pass was still running and
recorded a caveat about partial string coverage that later proved false. Final state is 557,719
symbols; the mid-pass sample showed 124,871. That caveat is withdrawn in the log. Take metrics only
after a pass finishes.

**ReGenny attach needs both parameters.** `regenny_attach` requires `pid` *and* `name` together;
either alone errors. Module names in its Lua API are **full paths**, so `get_module("PreyDll.dll")`
returns nil — match on a path suffix instead.

## Mechanics risk analysis

[`VR_MECHANICS_RISK.md`](VR_MECHANICS_RISK.md) ranks Prey's mechanics by VR difficulty, grounded in
binary strings rather than recollection, with evidence and judgment kept separate. The three needing
design decisions before camera ownership hardens:

1. **Zero-G** — `RollSpeedZeroG` means the engine rolls the view, and `zeroGUpAddition` means the up
   vector is not fixed. Mandatory content (GUTS, EVA).
2. **Cinematic camera takeover** — `Actor:PlayerCinematicControl` and `CinematicVTOLUpdate` fight the
   pose injection for the same transform, and gate the opening minutes.
3. **Mimic Matter** — `ArkPsiPowerMimicMorphInObject` confirmed; the player becomes an object with no
   body, scale, or hands.

**This breaks existing code.** `MakeBoundedYawProbe` in [`../src/common/AimState.cpp`](../src/common/AimState.cpp)
builds a Z-up yaw bounded to 15 degrees, valid only while world up is meaningful. In zero-G the
player basis is arbitrary, so the detached-aim math underpinning the A0b and interaction proofs does
not hold there. Those proofs stand — both were captured in normal gravity — but the aim lane needs a
basis-independent formulation.

## Highest-value open thread

`e_ArkLookingGlass` ships with this help text:

```text
0 disabled (renders normally)
1 use Scene Windows to look into the other scene
2 show only the main scene
3 show only the second scene
```

**Prey already renders a second scene** through in-world Looking Glass windows. The committed
per-eye route is mod-owned scene re-entry, and this is evidence the renderer already contains
machinery for rendering an additional scene view in one frame.

This does not contradict the H-001 closure — that was about a stereo control surface and the view
block's camera count, and in-world scene windows are a different mechanism. But if it generalises to
a second camera it could materially cut the cost of the route just committed to.

It is a live cvar with four documented modes, so it is observable **without writing anything**. This
is the cheapest high-value test available and was not started.

## Risks and loose ends

**The repository has no commits.** Every file is untracked, and this lane touched `src/`,
`tests/`, `tools/`, `cmake/`, and `regenny/` — exactly where a parallel Codex lane is most likely to
collide. There is no baseline to diff or recover to. This was raised twice during the session and is
still outstanding. It is the single largest risk on this page.

**Date inconsistency in the log.** Research-log entries and capture filenames from this lane are
dated `2026-08-01` to match the surrounding entries, but the work actually happened on 2026-08-03
and 08-04. In a project whose method depends on dated, build-identified evidence this is a real
defect. Not corrected unilaterally because it would rename capture files that other documents link
to. Worth a decision.

**R-025 is `static-only` and must not be hooked.** It has never been observed executing and its
object layout is inferred from COM vtable slot usage rather than a runtime read. It is in the gate
as a signature check only, which is safe because that is a read-only comparison.

**The mechanics ranking is unvalidated judgment.** Strings prove the systems exist; nothing there has
been runtime-traced. Treat it as a planning instrument, not evidence.

**Nothing in this lane wrote to game memory.** No hooks installed, no breakpoints left, no game files
modified. Ghidra is the only tool whose state changed, and those changes are annotations that were
intentionally saved.
